# 原型独立验证

## 输入与被测对象

输入包括已确认的需求与必跑用例、功能地图、测试数据、操作编号、实际候选、入口、作者标识和场景自测证据。核对待合入候选的父版本和实际提交，React 另核对构建记录的源码提交、依赖锁和成品摘要。独立审查的简报、自测报告和变更范围按以下交接小节核对。 [Superpowers 独立审查交接](../references/superpowers-workflows/SKILL.md#independent-review)

RTL 的行为结论以 Verifier 在被测候选上取得的独立证据为准。

| 模式 | 实际被测对象 | 记录身份和所需上下文 |
|---|---|---|
| `integration` | React 暂存提交的构建入口，或静态暂存入口，以及 `candidate` | 非作者，暂存 `operation_id` |
| `contract` | 同一暂存结果中提供方和使用方的实际组合 | 非作者，暂存 `operation_id`、`edge`、`version`，两方的 `task` 与 `commit` |
| `delivery` | `land` 返回的实际落盘入口与候选 | 非作者，交付 `operation_id`，实际路径和浏览器由报告带入 |

使用真实用户路径验证。暂存证据按待合入任务及契约双方追溯原作者和仅复验人员，落盘证据还核对候选及已登记的继承来源。独立证据的执行者须与这些变更及复验人员独立。

## 启动 → 环境核对 → 操作 → 取证 → 清理

1. **启动。** 查明实际 `index.html` 位置。正式交付从用户确认的最终目录以 `file://` 打开。用例与报告放在被测目录外，报告使用新路径。浏览器驱动装在验证环境，页面运行资源随原型交付。
2. **环境核对。** 核对目标提交、操作编号、实际浏览器、数据修订和用例修订。暂存工作区保持待验提交完整。选择当前项目可复现的数据。测试数据修订只标识输入，页面状态必须由已有本地数据或实际页面操作触发。
3. **操作。** 从真实入口驱动页面，至少执行一个可观察断言。异步路由切换后用 `visible` 等待目标页面的唯一标题或控件。关键用例检查用户操作后的状态和可见副作用。按已确认要求检查刷新回读、禁用、空态及错误。截图可以辅助风格复核，行为以执行结果为证。
4. **取证。** 保留浏览器报告、失败步骤、实际入口及候选。对照必跑清单，区分通过、失败、受环境阻塞与未执行。正式落盘对每个已登记的验收浏览器执行完整必跑清单。相同内容移到另一落盘路径后，重新从新入口验证。补充用例已在验收范围内报告失败时，保留失败，并在同一浏览器引擎上用原用例定义复验。
5. **清理。** 浏览器执行器为每个用例建立并关闭独立上下文。清理测试临时环境时保留原始报告、台账、用户文件和已落盘原型。

这五步参考 pstack 的验证流程。文件入口采用 Playwright 上游的真实文件 URL 测试思路。 [pstack 验证 Skill](../references/pstack-workflows/SKILL.md#create-verification) · [Playwright 文件入口测试](../references/engineering-verification/SKILL.md#file-url-verification)

## 功能地图实走与故障归因

按功能编号逐项比对地图、实际路径和报告步骤。 [pstack 功能地图维护](../references/pstack-workflows/SKILL.md#maintain-verification)

暂存验证从候选的实际 `index.html` 进入，覆盖受影响功能的路由、页面标识、用户动作及已冻结的可观察结果。报告或交接关联功能编号、用例编号、实际入口和候选。`map-check` 用于预检文件路径和关联。

落盘验证从 `land` 返回的正式 `file://` 入口执行完整必跑清单。新轮使用 `browser ENTRY SUITE REPORT --feature-map PROJECT/docs/feature-map.md --feature-entries` 核对实际地址及可见的 `data-rtl-feature` 和 `data-rtl-scene`。正式验收还要求冻结的业务断言在约定步骤和地图登记入口通过，并核对断言前的操作顺序。跨路由用例在各相关功能的登记入口验证对应断言，报告保留步骤位置。页面标记和业务断言均须通过。

| 实走结果 | 归因和证据 |
|---|---|
| 用户行为符合冻结预期，地图的入口或说明过时 | 记录功能编号、实际入口、地图差异和受影响条目。 |
| 用户行为符合冻结预期，选择器、步骤或数据准备使验证无法执行 | 记录阻塞步骤、用例编号和实际数据修订。核对修订后的验证方式时沿用原用例编号和冻结预期。 |
| 用户行为偏离冻结预期 | 保留失败证据，标明功能编号、实际行为与预期差异，验收规则有歧义时列明具体条款。 |

复验已交付版本时，只读核对原候选、实际入口和验收清单，在独立路径保留报告。

## 缺陷的旧版复现与修复复验

旧版与修复版的对照方法参考本地工作规范。 [pstack Bug fix](../references/pstack-workflows/SKILL.md#bug-fix)

对可复现的缺陷，保留原失败报告，或从可定位的旧候选在隔离环境重放用户路径。用相同的前置数据、业务步骤和断言核对旧候选的失败与修复候选的通过，分别记录版本、实际结果和报告位置。已有报告足以复现时直接引用。旧版本或数据不可用时，注明复现限制，仍按现有门禁验证修复候选。旧版结果作为问题依据留存，当前验收以当前被测对象的证据为准。同类缺陷再次出现时关联已有报告和候选。

## 用例和证据格式

使用本轮冻结的实际选择器、用例文件及数据。报告的文件摘要、用例编号及修订须匹配登记项。浏览器操作、用例格式和环境设置见 [运行手册](../../docs/runbook.md#浏览器验证合入和交付)。

跨场景联验按当前冻结用例操作实际提供方，再从实际入口验证使用方的结果。需要拒绝操作时，核对反馈和数据是否保持原状。独立场景在最终候选上运行各自的必跑用例。

在 Loop 工具目录运行浏览器并登记证据。`KIND` 使用 `integration`、`contract` 或 `delivery`，其余变量填实际路径和返回编号。正式落盘验证按上文带功能地图参数。

```sh
python3 -m loop browser "$ENTRY" "$SUITE" "$REPORT"
python3 -m loop --data "$DATA" evidence "$RUN" "$KIND" "$SHA" --actor "$ACTOR" --context "$CONTEXT" --report "$REPORT" --epoch "$EPOCH"
```

集成和落盘上下文使用各自的 `operation_id`。以下是契约联验的上下文示例。

```json
{
  "operation_id": "merge-OP",
  "edge": "classification-query",
  "version": "v2",
  "provider": {"task": "A", "commit": "A_SHA"},
  "consumer": {"task": "B", "commit": "B_SHA"}
}
```

驱动报告包含实际 `file:` 入口、浏览器版本、数据和用例修订、资产及用例摘要、已执行步骤、错误和用例结果。以 `--report` 提供实际原始报告，RTL 使用同一份字节解析、计算摘要并归档。验证交接记录包含证据编号、测试对象、必跑覆盖、失败及未执行项。适用的失败保持对应门禁阻塞，契约用例按当前组合及冻结锚点判定证据归属。

## 阻塞与复验要求

- 入口打不开、资源缺失、环境无可用浏览器或测试数据无法重现时，报告具体阻塞。复验沿用文件入口。目标浏览器范围或验收预期有歧义时，列出待确认项。
- 行为失败时提供步骤、实际结果和受影响的功能编号，注明涉及场景实现、共享接线或契约的观察。复验使用修复后的实际被测版本。
- 版本、路径、操作编号或执行者不匹配时，查回真实对象重新验证。验证记录保留观察结果及覆盖范围。
