# RTL 多 Agent 并行原型 Loop

## 范围

RTL 将业务需求拆成可独立验收的场景。Master 按条件派发，Integration Agent 滚动集成，独立验证 Agent 验证实际候选。设置两个场景并发位和一个集成写入者。用户收到的页面原型可以直接双击 `index.html` 打开，样式、脚本、素材和运行所需的 Mock 随包提供。

新项目源码采用 React + Umi + Ant Design。Loop 按精确源码提交隔离安装依赖并构建，保存依赖锁摘要与成品清单。场景自测、暂存联验、正式落盘回归分别绑定相应源码及成品。交付回执提供同一提交的源码交接目录。

## 三处目录

| 位置 | 职责 |
|---|---|
| Loop 工具项目 | 工作约定、当前 Skill、调度和校验模块、通用故障用例 |
| Loop 持久数据目录 | 项目及运行身份、候选、隔离工作区、派发和交付回执、运行台账中的活动契约与版本记录、版本化的验证脚本及测试数据、原始证据 |
| 独立原型项目 | `prototype/` 下的页面与资源，`docs/` 下的功能地图、风格和变更索引，`memory/` 下的项目身份、确认基线和变更记忆 |

工具通过稳定项目编号和已确认的项目路径关联独立项目。S0 确认最终落盘入口，常规位置是项目的 `prototype/index.html`。用户指定独立交付位置时，将该实际入口写入台账。原型项目保留业务验收口径，执行和恢复资料由 Loop 持久数据目录按版本管理。

## 角色与阶段

| 阶段 | 负责人及放行依据 |
|---|---|
| S0 启动 | Master 核对项目编号、实际路径、现有文件、基础版本和在途运行。区分新建、续跑和新一轮，分别控制项目与落盘路径的唯一活动写入权。 |
| S1 需求 | Requirement Architect 按可独立验收的结果拆场景。冻结范围、验收预期和必跑清单，将功能、场景、适用契约及用例建立关联。 |
| S2 场景 | Integration Agent 提供源码底座、共享资产和构建入口。Master 交接当前风格、任务和已登记的设计结论，按条件派发。场景 Agent 实现源码，通过该提交的构建成品自测。 |
| S3 集成 | Integration Agent 在当前父版本上生成待合入源码并构建成品。独立验证范围按 [主控暂存联验](../skills/loop-control/SKILL.md#暂存联验与提升) 确定。证据与精确提交、成品及当前父版本匹配后提升候选。 |
| S4 交付 | 锁定候选，暂存完整目录并校验内容，登记交付意图后放入确认路径并标记待验。独立验证 Agent 从实际 `file://` 入口跑必跑清单，在功能地图的登记入口核对业务断言。Master 裁决后登记交付并回写项目记忆。 |

角色只在各自授权范围内执行。用户确认项目路径、业务范围和验收预期，裁决关键风格或业务取舍，并按本轮约定参加人工验收。技术必跑证据缺失时保持待验。

## 派发和契约

派发简报至少包含任务、尝试编号、基础版本、允许写入范围、依赖、上游证据、契约及风格引用和完成条件。具体交接由 [主控调度](../skills/loop-control/SKILL.md#派发简报和宿主交接) 维护。

1. 任务包和底座就绪即可领取设计、协商共享接口，或领取条件齐备的独立实现任务。
2. 实现任务声明的接口经双方确认且由 Master 激活后，按所绑定的契约与 Mock 开工。
3. 提供方及使用方实际产物就绪后，按同一候选做跨场景联验。

等待的场景在核对实际工具停工或完成工作区隔离后释放并发位。已确认停工且输入仍有效时，沿用原尝试恢复。隔离后新开尝试使用独立工作区。共享文件指定唯一写入者。执行依赖成环时合包或重新拆分。

S1 业务依赖描述业务规则，技术依赖描述提供者及开工条件。S2 接口契约描述具体字段、状态、异常和共享测试样例。提案绑定当时的激活状态，依据失效或版本退役后以新版本重新提出及确认。该边首次激活时，可沿用尚未绑定版本的设计。后续改版使涉及该边的无版本或过期设计交接失效，并沿实际依赖定位受影响实现与证据。兼容过渡需在现行契约明确支持范围，并对具体的提供方、使用方、契约和冻结测试输入组合留证。破坏性变更通过同批联验或经验证的过渡方案合入。

## 持久状态和恢复

派发、候选提升、交付先登记操作意图，副作用完成后记录回执。操作编号标识同一次副作用，尝试编号标识一次执行。Master 接管使旧主控失去写入权，仍在隔离工作区执行且输入有效的场景可以继续。

- 派发回执缺失时查询原尝试。通过停工或隔离核对后，撤销原尝试的提交资格再替换。
- 合并回执缺失时对比实际候选、预期父版本和预登记结果。实际结果已经匹配时只补回执，父版本改变时另建结果并复验。
- 交付回执缺失时核对实际目录、内容标识和验证结果。实际目录刚就位时继续标记待验。验证、记忆和索引按同一交付及变更编号补写。待验替换被驳回时，按原交付操作核对备份并恢复已验收入口。 [运行手册](runbook.md#浏览器验证合入和交付)
- 新调用读取当前本地 Skill 并记录内容标识。执行模块和本轮冻结基线负责硬门禁。旧尝试及证据按当时实际的输入与结果核对。

## 证据与交付

证据标明实际被测版本、用例、执行者、环境、脚本和数据版本、预期、实际结果及证据位置。分别记录通过、失败、阻塞和未执行。报告的结果、摘要和归档来自同一原始内容。功能地图用稳定编号关联业务预期和用例。对关键变更检查验证者独立性。

正式验证在实际落盘的文件入口运行完整必跑清单，涵盖冷启动、关键业务路径和约定的保存回读。交付内容身份覆盖原型资产。验收结论引用同一候选的证明及实际路径。变更记忆记录结果，变更索引提供链接。试点用目标浏览器实测文件入口和存储行为，按实测范围说明支持情况。
