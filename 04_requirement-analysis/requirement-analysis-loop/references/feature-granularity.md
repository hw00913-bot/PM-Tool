# 功能清单的拆分与范围标准

适用于 S7 生成功能清单、增量变更和 G3 复核。规则版本 `business-operation@2`：先固定版本、系统边界、本期交付责任，再拆功能。这是本 Loop 的 FUNC 业务条目规则，不是标准功能点计量算法。核心判定同时写在 SKILL.md，不能因只复制入口文件而丢失。

## 一条 FUNC 的定义

功能草案预生成与原型后优化遵循 SKILL.md 的“两轮确认”：需求事实为依据，流程／接口补全，原型双向核验。不能仅从流程枚举功能，也不能仅从原型按钮反推交付范围。原型提出的细化、拆分／合并或新增范围须保留证据与版本差异，经确认后回本 Loop 更新；旧冻结包与原报价不自动改变。

**一个业务对象上的一个主要业务操作，产生一个可独立验收的结果。** 保留明确系统边界和业务触发，但不再用“一个完整场景／业务生命周期”作为功能大小。

功能名称宜为“动词＋业务对象”，例如开通坐席、停用坐席、发布呼叫方案、导出统计报表。不能只用“人工外呼”“坐席生命周期管理”“通话记录与统计审计”等业务域名称打包多个独立操作。名字换成动词而说明仍捆绑多种操作，也不合格。

- 用户可以是人、设备或外部系统；后台无页面也可以构成独立功能。
- 完成结果可以是稳定业务状态、查询结果或输出，不要求整个业务旅程结束。例如“创建待支付订单”可以是完整结果，不必与最终入账捆成一项。
- 可独立验收不等于独立部署、无依赖；应能明确输入／前置条件、执行范围和完成判据。

## 拆分、合并与停止条件

1. **按业务对象和主操作拆**：先从 US/AC、SC 步骤及已确认页面行为提取业务动作，再归并必要明细，最后分配 FUNC。不同业务触发／生命周期时点、分别形成可验收结果的动作必须分别列项；不得按 SC 顺序每个场景只写一行功能。
2. **在完整结果处停止**：继续拆就只剩字段、按钮、校验、技术调用或必要错误反馈时，停止拆分；这些记录在范围、规则、异常和验收中。底层 API 数量、页面数量、开发工时都不是 FUNC 个数。
3. **按业务实质识别差异**：目标、处理对象／数据、业务规则或完成结果实质不同，且可分别验收时，才有独立 FUNC 的依据。仅角色、入口、终端、渠道、文案不同，通常复用同一 FUNC；确有业务差异才拆，并写明理由。
4. **正常与必要异常一起交付**：字段非法、权限拒绝、重复提交、失败反馈等一般属于原过程。另有独立业务触发和结果的人工异常处理、重试补偿管理等，仅在需求明确纳入时独立拆分；不要凭常识增加范围。
5. **明确的独立操作不能合并**：新增与修改、开通／停用／恢复／删除、列表查询／详情查看／导出、配置保存／发布／切换默认，在需求明确可分别操作并形成不同结果时分别成项。不能以“同属 CRUD／同属生命周期／共用弹窗”合并；也不能自动补齐未要求的操作。查询中的筛选、排序、分页通常共同构成一个查询结果。
6. **避免重复计算**：跨页面／角色共用一个 FUNC；公共能力集中引用，不在每个调用方重复登记。真实不同功能可共用代码，不能因复用实现就强行合并业务过程。

上游把按钮、字段或接口列为交付要求时，必须保留该要求及其 AC；先判断是否真的形成独立业务过程，不因其“被单独提及”就自动登记新 FUNC。技术交付、非功能要求和实施任务可单独跟踪，但不能冒充业务功能或因不计入 FUNC 而被遗漏。

“不按按钮拆”只排除纯 UI 控件，不排除按钮背后的业务操作；“停用”“发布”“导出”若有独立结果，仍需单列。独立权限可辅助识别边界，但不是独立功能的必要条件；相同角色也可以执行多个独立功能。

## 场景到操作的拆分复核

每个场景先枚举候选业务操作，再区分“独立操作／主操作明细／复用既有功能／待确认边界”，不得直接把场景标题复制为功能名称。

- 配置、执行、结果接收处理、查询统计可能位于同一场景，但具有不同触发和结果；不能仅因都服务于“完成外呼”就打包成一条。
- 创建时必填的名单上传、参数填写或重呼策略可以是创建明细。是否允许后续独立修改、独立上传或发布，需要上游证据；不要为变细新增入口。
- 供应商内部算法、媒体链路处理不是自动新增的本方业务功能；只列本方明确承担的配置、调用编排或结果处理，并注明依赖。
- 单次自动处理中的幂等、回滚、自动重试通常是明细；用户可单独发起的失败重试有独立触发和结果，可另列。材料只说“可重试”时先记录待确认，不能擅自承诺人工重试页面。
- 同一发起能力在工作台、监控页或详情页复用同一 FUNC。不能一边计“人工外呼”，又因监控入口计一个内容相同的“从监控发起人工外呼”。

复核结果写入各功能的 `boundary.split_rationale`：明确哪些已识别操作拆到哪些 FUNC、哪些组成部分未单拆及原因。只有 Markdown 的草案须附“来源场景／独立操作／功能归属或明细／理由”的复核表。表中若用旧清单定位，标明“原 FUNC”，不能把原粗粒度 ID 静默赋给多个新功能。

SC 数和 FUNC 数相同且一一对应是复查信号，不是按数量自动判错的依据。检查的是操作有没有被打包、漏掉或重复；不设“至少拆多少项”或“每个场景至少几项”的配额。

## 必须留存的范围证据

保留现有总览列：版本、一级模块、二级模块、可选三级模块、功能名称、功能说明、备注、修改类型，以及稳定 FUNC ID 和 US/AC/SC 来源。

每项另附 `boundary`：业务对象、单一主操作、系统／交付责任边界、发起方、触发事件、主要目的、完成结果、包含范围、不包含范围、处理规则、异常范围、依赖、假设、拆分／合并依据。字段含义及 JSON 形态见 [产物契约](artifact-contracts.md)。

- 包含范围要具体到本期承诺的业务处理，不写“相关功能”等无限兜底表述；说明依赖方内部实现不属于本方交付的部分。
- 验收复用 `source_acceptance_ids` 的已确认 AC，不另造一套冲突标准。范围明细中列出 AC ID 与对应判据；不足时回上游补齐再冻结。
- 列表 `[]` 表示已确认没有此项，不表示未知。未知或争议写假设与 `open-items.json`，沿用风险门禁，不为满足必填而编造。
- `change_detail` 记录变更前、变更后、本轮改变范围。迭代写明原版本或基线定位；新增的变更前为 `null`。未改变的存量功能不是本轮“新增／迭代”行，可在依赖／范围中引用。
- FUNC 对外引用后保持稳定，不因移动模块、排序或增加页面而重编号。真正拆分／合并既有功能时记录旧 ID、替代关系与影响，并重新确认基线，不能静默复用旧 ID 改变含义。

## 说明文档与报价的使用边界

功能清单说明交付什么，范围明细说明包含到哪里，报价说明如何估算与计价。三者关联，不等同。

- 一条 FUNC 不等于一个 IFPUG 功能点、一个 COSMIC CFP、一个开发任务或一个等价报价单元；禁止“功能行数 × 统一单价”冒充标准计量。
- 只有用户明确要求时生成说明文档、标注或报价。以冻结版本、FUNC、范围、AC 和变更差异为依据，不只复制功能名称；范围未确认时明确报价假设／限制，不能当确定承诺。
- 报价可以一项对应多个 FUNC，一个 FUNC 也可按工作类型分解估算，须说明关联并避免重复计价。公共基础能力、非功能约束、部署、迁移、集成与实施工作应另列并明确包含关系，不能通过虚增 FUNC 数补费用。
- 原型可把同一 FUNC 拆为多个页面、组件、状态与验证步骤；这些是实现任务，不能反向扩大功能或改变已冻结范围。

## 复核示例（仅用于判断，不自动纳入充值项目）

| 候选项 | 判断依据 |
| --- | --- |
| 发起充值申请 | 创建有效待支付订单并给出支付入口，可形成完整结果 |
| 支付结果确认与入账 | 外部结果触发，完成核验、订单与账务更新及防重复入账；可与申请过程分开 |
| 充值记录查询 | 在确认条件下返回查询结果，通常有独立目的与验收 |
| 充值记录导出／人工异常单处理 | 仅在需求明确纳入且具独立结果时登记，不默认追加 |
| 金额输入、提交按钮、签名校验、重复回调处理 | 通常是上述过程内部组成，纳入对应范围／异常／AC，不分别计 FUNC |

## G3 人工评审问题

逐项确认：能否写出一个业务对象与一个具体主操作？是否包含另一种独立触发和结果？是否遗漏已要求的启停、查询、导出、发布或后台处理？是否只是把场景重命名为功能？再拆是否只剩控件／技术步骤？是否因共用入口、角色或实现而误合并／重复登记？正常与必要异常是否齐全？责任、排除项和版本差异是否清楚？是否有对应 AC 的正文依据？

脚本核对对象／主操作及其余字段、类型、来源覆盖与视图同步，并拒绝“管理／全生命周期管理”等明显泛化主操作。它不能识别所有换名后的功能包，不能证明语义上的最小性、无重复或工作量正确。G3 必须展示操作归属复核与争议，不用自动通过替代确认。

## 方法参考与限度

借鉴 IFPUG 基本过程和 COSMIC 功能过程的用户视角，不宣称本清单已经完成任何标准功能点计量。若合同要求标准计量，应另选定方法、版本、计量边界并完整应用该方法，不能混合两套规则或将物理接口调用数视为标准计量结果。

- [IFPUG 功能点分析概述](https://ifpug.org/ifpug-standards/fpa)；[ISO/IEC 20926:2009 标准信息](https://www.iso.org/standard/51717.html)。
- [IFPUG MetricViews 2015 基本过程说明文章](https://ifpug.org/wp-content/uploads/2021/10/MetricViewsAugust2015.pdf)是解释资料，不代替完整规范。
- [COSMIC 方法介绍](https://cosmic-sizing.org/cosmic-sizing/intro/)与[术语表](https://cosmic-sizing.org/cosmic-sizing/cosmic-glossary/)。
